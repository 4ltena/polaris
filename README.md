# polaris

総消費量の計測、圧縮閾値、ローカルの履歴保管・意味検索は[コンテキスト効率化](docs/context-efficiency.md)を参照。

polaris は、codex の改良版ハーネスである。最大の制約は、毎ターン
モデルへ送る常時コンテキストを 990 トークン以下に保つことにあり、この数値は
見積ではなく `tiktoken_rs::o200k_base()` による実測で担保する。

CLIの一回実行とTUIでの対話・再開に対応する。パスポリシー付きのツール、
OpenAI互換プロバイダ、監査ログ、停止条件、履歴圧縮を備える。
`--remember`を指定した会話では、圧縮前の履歴を保存し、プロジェクト別に検索できる。

## ビルド

Rust 1.96.0（`rust-toolchain.toml` で固定）、edition 2024 を使う。

```
cargo build --release
```

バイナリは `target/release/polaris` に生成される。

## 環境変数

| 変数 | 既定値 | 意味 |
| --- | --- | --- |
| `POLARIS_PROVIDER` | `openai` | `openai` か `codex`。`codex` は `polaris login` で得た ChatGPT のサブスクリプション認証を使い、API キーを要しない。 |
| `POLARIS_API_KEY` | なし | `POLARIS_PROVIDER=openai` のとき必須。OpenAI 互換エンドポイントの API キー。 |
| `POLARIS_BASE_URL` | `https://api.openai.com/v1` | `POLARIS_PROVIDER=openai` のときのベース URL。 |
| `POLARIS_MODEL` | `gpt-5.4` / `gpt-5.6-sol` | 使用するモデル名。既定はプロバイダごとに異なる。`codex` の既定は `codex debug models` の実カタログで確認できる。 |

`polaris --help` にも同じ内容を載せてある。

## 監査ログ

`--audit <path>` で出力先を指定できる。省略すると
`~/.polaris/state/<project-id>/audit.jsonl` に書く。`<project-id>` は作業
ディレクトリの canonicalize 済みパスから求める識別子で、作業ディレクトリの
外（ホーム配下の状態ディレクトリ）に書くのは、リポジトリを `git add -A`
した瞬間に伏字化の取りこぼしがコミットへ混ざるのを避けるためである。1 回の
ツール呼び出しにつき 1 行の JSON を追記し、書き込む前に必ず秘密情報の伏字化
を通す。

## 実行

```
POLARIS_API_KEY=sk-... polaris -p "Cargo.toml は何行か"
```

`cargo build --release` の前であれば `cargo run -p polaris-cli --` の後に
同じ引数を続けてもよい。これが M1 の受け入れ基準そのものであり、動けば
`Cargo.toml` の行数を含む答えを標準出力へ返す。

## サブコマンド

`codex` CLI(0.148.0 時点、24 個のサブコマンド)を調べたうえで、polaris の
既存アーキテクチャ(単一の one-shot 実行経路、`polaris-sandbox` クレート)へ
素直に載る範囲だけを移植した。

- `polaris exec [PROMPT]` — `--prompt`/`-p` と同じ one-shot 実行の別名。
  引数を省略するか `-` を渡すと標準入力から指示を読む(`codex exec` と同じ
  規約)
- `polaris sandbox -- <コマンド...>` — エージェントループを介さず、
  `--sandbox` で選んだポリシーの下で任意のコマンドを直接実行する。実際の
  終了コードと標準出力/標準エラーをそのまま返す。ポリシーが何を許可するか
  を単体で確認するための道具
- `polaris doctor` — 保存済み資格情報(`~/.polaris/auth.json`・
  `api_key.json`)の有無、`POLARIS_PROVIDER` 未設定時にどちらへ倒れるか、
  サンドボックスバックエンドの可否を診断する。すべて読み取り専用で、鍵の
  中身自体は一切表示しない
- `polaris completion <bash|zsh|fish|elvish|powershell>` — シェル補完
  スクリプトを標準出力へ生成する(`clap_complete` を使用)

以下は `codex` にあるがこのバージョンでは移植していない。polaris 自体が
持たない基盤を新たに一つ作る規模の作業になるため、意図的に対象外とした:

- `mcp` / `mcp-server` — polaris は MCP クライアント/サーバを一切持たない
- `app` / `app-server` / `remote-control` — デスクトップ GUI・実験的リモート
  デーモン。polaris はヘッドレス CLI と TUI のみ
- `cloud` — Codex Cloud という codex 独自のバックエンドに依存する
- `exec-server` / `plugin` / `update` / `migrate-rollouts` / `debug` /
  `features` — いずれも codex 自身の内部基盤(実験的サービス、プラグイン系、
  自己更新、legacy セッション移行、内部デバッグ/feature flag)に紐づき、
  polaris に対応物が無い
- `resume` / `fork` / `archive` / `delete` / `unarchive` — codex の複数
  セッションピッカーに相当する。polaris の TUI は現状 1 プロジェクトにつき
  1 セッションのみを永続化する設計(`docs/superpowers/CURRENT.md` 参照)で、
  複数セッション管理は既存の永続化フォーマットに影響する別途の設計を要する
  ため、今回は見送った
- `review` — 非対話のコードレビュー実行。one-shot 経路の上に乗せられる
  見込みだが、レビュー用プロンプトの設計を要するため今回は見送った

## subagent（`spawn` ツール）

`spawn` は、下請けのエージェントを1波でまとめて走らせるツールである。各
subagent は自分専用のシステムプロンプト、許可ツールの部分集合、サンドボックス、
ターン数と壁時計の上限を持った独立したループで動き、型が宣言した JSON Schema
に照合済みの結果だけを親へ返す。途中で読んだファイルや失敗したツール呼び出しは
親のコンテキストへ一切入らない。常時コンテキストを 990 トークンに保つという
制約と、大きな調査を分担させたいという要求は本来ぶつかるが、`spawn` は後者を
前者の外側へ追い出すことで両立させる。

深さは1に固定してある。subagent へ渡すツール一覧からは `spawn` を無条件で
除くため、subagent がさらに subagent を起動する経路は存在しない。

戻り値はタスク1件につき1要素の JSON 配列で、順序は与えたタスクの順に一致する。

```json
[
  {"type": "file-inspector", "ok": true,  "result": {"path": "src/agent.rs", "responsibility": "..."}},
  {"type": "file-inspector", "ok": false, "error": "schema mismatch after retry (SchemaMismatch): ..."}
]
```

同じ波の2つのタスクが重なる `write_root` を宣言した場合は、1件も走らせずに波
全体を却下する。その場合も形は変わらず、全要素が `"ok": false` の配列を返す。

### 設定

`~/.polaris/config.toml` と `<project-root>/.polaris/config.toml` を読み、
後者が優先する。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `[agents] paths` | `[]` | subagent 型を探す追加ディレクトリ。既定の2か所（`<project-root>/agents`、`~/.polaris/agents`）は常に探すので、ここへ書くのはそれ以外の場所だけでよい。 |
| `[spawn] concurrency` | `8` | 1波が同時に走らせるタスク数の上限。 |
| `[spawn] write_concurrency` | `4` | 同時に走るタスクのうち、`write_root` を持つものの上限。書き込みは読み取りより I/O が競合するため `concurrency` より狭く取ってある。 |

```toml
[agents]
paths = ["/Users/me/shared/agents"]

[spawn]
concurrency = 8
write_concurrency = 4
```

### subagent 型の書き方

1つの型は `agents/<型名>/SKILL.md` 1ファイルで定義する。ディレクトリ名と
frontmatter の `name` は一致していなければならない。リポジトリに同梱の
`agents/file-inspector/SKILL.md` がそのまま最小の実例である。

```markdown
---
name: file-inspector
description: 単一ファイルを読み取り専用で棚卸しし、責務、入出力、対応するテストを返す。
allowed-tools: read
metadata:
  polaris-access: read
  polaris-tier: low
  polaris-wall-seconds: "360"
  polaris-max-turns: "12"
  polaris-continuation: "denied"
  polaris-output: references/result.schema.json
---

あなたは単一ファイルを棚卸しする subagent である。与えられたパスを
`read` で読み、次の JSON だけを出力として返す。他のテキストを含めない。
```

frontmatter 直後の本文が、その型のシステムプロンプトになる。`allowed-tools`
は空白区切りで、ここに書いた名前のうち `spawn` を除いたものだけが実際に渡る。

`metadata:` の6キーはすべて必須で、1つでも欠けるとその型は読み込まれず、
起動時に理由付きで読み飛ばした旨が標準エラーへ出る。

| キー | 取りうる値 | 意味 |
| --- | --- | --- |
| `polaris-access` | `read` / `read-write` | サンドボックスの強さ。`read` は読み取り専用で固定する。`read-write` の型は、呼び出し側が `write_root` を指定しなければ実行を拒否する。その `write_root` が親自身の書き込み可能ルートの外にある場合も拒否する。 |
| `polaris-tier` | 任意の文字列 | 型の重さの分類。現時点では読み取るだけで、実行時の挙動には影響しない。 |
| `polaris-wall-seconds` | 秒数 | 1タスクの壁時計上限。超えるとそのタスクだけが失敗として返る。 |
| `polaris-max-turns` | ターン数 | 1タスクのターン上限。スキーマ不一致による1回の再試行も同じ予算から引く。 |
| `polaris-continuation` | `denied` / `allowed` | 波をまたいだ継続の可否。下記の制限を参照。 |
| `polaris-output` | 相対パス | 結果を照合する JSON Schema のファイル。型自身のディレクトリの内側に限る。絶対パスや `../` で外へ出る指定は読み込み時に拒否する。 |

出力がスキーマに合わなかった場合、検証エラーを添えて1回だけ再試行する。2回目も
合わなければそのタスクは失敗として返る。再試行は同じターン予算と同じ壁時計を
引き継ぐので、`polaris-max-turns: 12` の型が実際に24ターン使うことはない。

### 現時点の制限

`polaris-continuation: allowed` は frontmatter として受理され `AgentType` にも
保持されるが、実行時には参照していない。波をまたいで同じ subagent を継続させる
経路そのものが未実装であり、`allowed` と書いても `denied` と同じ挙動になる。

## skill/plugin を大量に含めた場合の比較

*skill/plugin 分類機（BM25ルータ）はv0.2.0 “Aldebaran”で導入した。製品全体の変更は[変更履歴](CHANGELOG.md)を参照。*

polaris の設計上の主張は「常時コンテキストは skill 数に依存しない」ことである。この主張を、実際に skill/plugin を大量に読み込ませた状態で codex・pi・polaris の三者を比較して検証した。

### 方法

codex 側の curated リポジトリから実際に収集した 831 件（skill 646 件、plugin 185 件。plugin はそのまま `SKILL.md` にならないため、`plugin.json` の `name`/`description` を frontmatter に写した最小の `SKILL.md` として書き出した）を、`codex`・`pi`（`--model openai-codex/gpt-5.6-sol`）・`polaris`（`POLARIS_PROVIDER=codex`）それぞれのネイティブな skill 探索先へ実ファイルとしてそのまま設置した。macOS の大文字小文字を区別しないファイルシステムで 1 件だけ衝突し、実際に設置されたのは 830 件である。

同一のタスク（`reverse_string` を実装し、対応するテストファイルを書く）を、この 830 件が設置された状態で 3 者へ同一プロンプトで 1 回ずつ実行し、実際の API 応答が報告する使用量（`usage`）とプロセスの壁時計時間を測った。トークン数は見積ではなく、各プロバイダが応答に含めて返す実測値である。1 回きりの実行なので壁時計時間には測定ノイズがあるが、トークン数の差は構造的なもので毎回同じ形で出る。

### トークン数

3 者とも実 API 応答の使用量から取った初回ターンの入力トークン数（見積ではない）。polaris の値は skill 数によらず常に同じであり、この不変性自体が主張の核なので 0・5・830 件のどの行にも同じ値を置いている。

| skill 数 | codex | pi | polaris | pi/codex | polaris/codex |
| --- | --- | --- | --- | --- | --- |
| 0 | 30,612 | 1,195 | 547 | 3.9% | 1.79% |
| 5 | 31,464 | 1,822 | 547 | 5.8% | 1.74% |
| 830 | 44,292 | 110,692 | 547 | **249.9%（2.5 倍）** | 1.23% |

codex は skill 数が多いとき、通常時の「name + description + 絶対パス」形式から、「name + 短縮パスのみ」（`skill roots` テーブルで絶対パスを間接参照する）という description 抜きの圧縮形式へ自動的に切り替える。そのため 0→5 件の区間（約 170 トークン/skill）と比べると、5→830 件の区間（825 件分、サンプルが大きく安定している）では約 15.55 トークン/skill まで下がるが、0 にはならない。pi にはこの種の圧縮が無く、0→5 件でも 5→830 件でもほぼ同じ比率（約 125〜132 トークン/skill）で線形に増え続け、830 件時点で初回ターンだけで 110,692 トークンに達する。

pi/codex の比は、少数の skill では pi の方が codex よりずっと軽い（4〜6%）のに、830 件では逆転して pi が codex の 2.5 倍になる。5〜830 件の区間の傾きだけで比べると pi は codex の約 8.5 倍重い。この傾きをそのまま外挿すると、およそ 260 skill 付近で両者の総量が逆転する計算になるが、5 件と 830 件の間に実測点が無く、codex の圧縮形式への切り替わりタイミングも未確認のため、これは見積もりであり実測ではない。polaris/codex の比は skill 数が増えるほど下がる——codex 自身が圧縮してもなお増え続ける分母に対し、polaris の分子が動かないため。

polaris は `lookup`（skill 検索）ツールを呼ばない限り、830 件設置後も常時コンテキストは 3 ターンでそれぞれ 547、600、747 トークンと、skill を 1 件も置かない場合と変わらない。これは `budget.rs` の不変条件テストが保証する性質を実運用でなぞったものである。`lookup` を実際に呼ばせた場合（同じ 830 件のコーパスに対する検索を明示的に指示したタスクで別途測定）は、その呼び出し 1 回につき数百〜数千トークンが該当ターンにだけ加わる——codex・pi のように毎ターン、使うかどうかに関係なく払い続けるコストとは性質が異なり、検索した回だけ・検索した分だけ払う。

候補リストは各候補の description を全文ではなく先頭文（`description_preview`、200 バイト上限）だけ表示する。実コーパス 831 件で候補リスト全体のレンダリングコストが 43,777→20,389 トークン（約 53% 減）になり、実際の `lookup` 呼び出し 1 回目の増分も、同じ 830 件コーパス・同じタスクでの計測で 1,234→624〜660 トークン（約 46〜49% 減）に下がった。先頭文だけに削っても、trigger 形式の近傍候補が量化語入りの判定節を保つ割合は 84 件中 83 件（98.8%）、BM25 が一致させた語がプレビューに残る割合は評価用クエリ 50 件中の該当ペア 41 件中 40 件（97.6%）で、削った分だけモデルが見誤って再検索する確率が大きく上がるわけではないことを、`docs/superpowers/CURRENT.md` に記録した評価用コーパスで確認している。

さらに、候補の並び順のうち先頭 `MAX_PREVIEWED_RESULTS`（8）件だけプレビューを残し、それ以降は名前のみを表示するよう変更した——`MAX_RESULTS`（20）自体は変えず、全件の名前は変わらず見える。安全性は同じ評価用コーパスで検証済みで、recall した 50 件中 31 件は上位 8 件以内に入り、5 件は 8 件目より後でも名前自体にクエリと一致する語が残っており、名前だけで一致しないのは 1 件（`description_preview` 導入時に既に許容していた既知の例と同一）だけだった。同じ 830 件コーパス・同じタスクでの `lookup` 呼び出し 1 回目の増分は、この変更でさらに 624〜660→344 トークンまで下がった（当初の 1,234 トークンから累計で約 72% 減）。

### 実行速度

同じ 830 件設置状態・同じタスクでの壁時計時間（1 回計測）。

| | 所要時間 |
| --- | --- |
| codex | 11.3 秒 |
| pi | 13.3 秒 |
| polaris（`lookup` を呼ばない場合） | 8.8 秒 |
| polaris（`lookup` を 2 回呼ばせた場合） | 13.9 秒 |

skill/plugin を大量に持つ場合、その分だけ余計に送受信・前処理するトークンが増える codex・pi よりも、常時コンテキストが変わらない polaris の方が今回の計測では速かった。ただし 1 回きりの計測であり、ネットワークやサーバ側の混雑による変動を切り分けていない。トークン数の差ほど確定的な主張はできない。

## ChatGPT のサブスクリプションで使う

API キーを持たない場合は、ChatGPT の認証で繋げる。

```
polaris login
POLARIS_PROVIDER=codex polaris -p "Cargo.toml は何行か"
```

`polaris login` はブラウザを開き、`http://localhost:1455/auth/callback` で
認可を受け取る。このポートは登録済みの redirect_uri のものなので選び直せず、
`codex login` とは同時に走らない。資格情報は `~/.polaris/auth.json` に 0600 で
保管する。`~/.codex/` には読み書きとも触れない。

`polaris logout` で保管した資格情報を消す。

### 保管先とパーミッションを手で確かめる

実際の資格情報を要するため、ここから先は自動テストで固定できない。手で追う。

`polaris login` を実行する前に、codex 側の資格情報の状態を控える。

```
shasum -a 256 ~/.codex/auth.json 2>/dev/null || echo "codex 側の資格情報は無い"
```

Linux では `sha256sum` を使う。`polaris login` のあとに同じコマンドを実行し、
出力が前と一致することを見る。`codex login` を一度も実行していなければ、
前後とも「無い」と表示される。それも正しい状態である。

polaris 側の保管先は次で見る。

```
ls -l ~/.polaris/auth.json
```

`-rw-------` であること。group と other に権限が残っていれば、同じホストの
別のユーザーがアクセストークンを読める。

### 期限切れからの更新を手で確かめる

`~/.polaris/auth.json` の `expires_at` を、過去の Unix 秒か `null` へ書き換える。
期限が不明な資格情報は毎回更新する扱いなので、どちらでも更新経路へ入る。行ごと
消してはいけない。`expires_at` は最後の項目であり、直前の行に余分なカンマが
残って JSON が壊れる。

その状態でもう一度実行する。

```
POLARIS_PROVIDER=codex polaris -p "Cargo.toml は何行か"
```

答えが返れば、`refresh_token` での更新を経てバックエンドへ到達している。
`polaris login` を促すエラーが出た場合は、更新そのものが失敗している。

更新のあとの `~/.polaris/auth.json` も見る。`expires_at` が未来の値へ進んで
いれば、更新結果が書き戻っている。`account_id` が空文字へ変わっていないこと、
パーミッションが `-rw-------` のままであることも併せて確かめる。

## TUI

`--prompt` を省略して `polaris` を実行すると、対話TUIに入る。

```
polaris
```

プロバイダの資格情報が無い状態で対話TUIを起動すると、資格情報が無いままエラーで終了する代わりに、
ChatGPTでサインインするかOpenAI APIキーを入力するかを選ぶ画面が出る
(`POLARIS_PROVIDER` が `openai`、つまり未設定のデフォルトの場合のみ。`codex` を明示した場合はこの画面には入らず、
従来通りの資格情報エラーになる)。APIキーは
`~/.polaris/api_key.json` に0600で保存され、次回以降は環境変数無しで使われる
(`~/.polaris/auth.json` とは別ファイルで、既存のcodexログイン情報には触れない)。
この画面は対話TUI起動時のみで、一発実行(`polaris -p "..."`)では従来通り即エラーになる。

事前にプロバイダの設定が必要である。`openai` なら `POLARIS_API_KEY`、`codex` なら
`polaris login` を済ませておくこと。プロバイダが未設定のまま `polaris -p` を実行すると、
旧来の「--prompt is required」ではなくプロバイダのエラーで失敗する。

`polaris` はどのディレクトリで起動しても常に空の会話から始まる。プロジェクトごとに1つの会話を
自動再開する挙動は無い——過去の会話を見るには `/resume` を使う(下記「スラッシュコマンド」節)。
実際に送信した会話は `~/.polaris/sessions/<会話id>.jsonl`(1メッセージ1行)+
`~/.polaris/sessions/<会話id>.meta.json`(起動元ディレクトリと開始日時)として、プロジェクトを問わず
1箇所にまとめて保存される。ファイルへの書き込みは最初のメッセージを実際に送るまで遅延される
——起動しただけで何も送らずに終了した場合、`/resume` の一覧に空の会話が残ることはない。
`Ctrl-C` で終了する。エージェント実行の内部ループでツールを呼び出す際の中間的なツール呼び出し・
ツール結果メッセージは個別に永続化されず、最終的なアシスタント応答だけが保存されることに注意すること。

画面上部には枠付きのヘッダーボックス(見出し行・モデル名/プロバイダー名・作業ディレクトリ・累積トークン
使用量)が常時表示される。`codex` の実際の対話TUIをtmuxで起動して観察し、dimスタイルの枠線+太字の
見出し行+ラベルを揃えた`model:`/`directory:`/`tokens:`各行というヘッダー構造、入力欄を
囲む枠を廃した`›`プロンプト(太字+dim、空欄時は "Ask polaris to do anything" とグレーで表示)、
入力欄下の2色構成フッター行(モデル名は暖色、ディレクトリは緑、区切りの`·`はdim)という構造を、
文言・配色の具体的な値はpolaris独自のまま踏襲した。見出し行冒頭のアイコンは、codexの`>_`(端末
プロンプト)をそのまま借りるのではなく、polarisという名前の由来である北極星にちなんで金色の
`✦ polaris`にしている。フッターの作業ディレクトリは`$HOME`配下なら
`~`で短縮表示する(実際のcodexのスクリーンショット`gpt-5.6-sol high · ~/File/projects/...`で
確認した表記。ヘッダーボックスの`directory:`行は引き続き絶対パスのまま——短縮されている根拠が
無いため)。
ツール呼び出しは会話履歴内に `⚙ ツール名(引数)` として、その結果は `→ 要約` として表示される
(結果が長い場合は200文字程度で打ち切られる。打ち切られるのは表示だけで、モデルへ送る内容には
影響しない)。`**太字**` と `` `インラインコード` ``、フェンス付きコードブロックは整形して表示する。

ターン実行中はステータス行に `Working`(shimmerアニメーション付き)+経過秒数+`esc to interrupt`が
表示される。`codex` の実際の `status_indicator_widget.rs`/`shimmer.rs` を読み、そのアルゴリズム
(ターン開始からの経過秒による2秒周期のスイープ、半値幅5文字のコサイン型グラデーション)をそのまま
移植した(色はcodexの端末色検出までは再現せず、固定のグレー→白のブレンドで近似している)。これを
実現するため、対話TUIのイベントループは非同期(`tokio::select!`でtick・キー入力・エージェントの
ターンを競わせる形)へ書き換えた。ターン実行中に`esc`を押すとそのターンを中断できる
(`session.messages`はユーザーの発言まで巻き戻され、`interrupted`と表示される。ツールが既に起動した
OSサブプロセスまでは強制終了しない——「待つのをやめる」だけの中断であることに注意)。

ターンが `--max-turns` 到達などで失敗した場合、そのターンで消費したトークン使用量はステータスバーの
累計に反映されない(失敗ターンの使用量は破棄される)。また、プロバイダが `usage` を返さない場合、
ステータスバーには実際には「不明」ではなく `0` と表示される(取得できなかった場合と初回起動時を
区別しない)。これらは大きめの再設計が必要なため、今回のリリースでは対応を見送り別途追跡している。

ツール実行の承認は画面内のモーダルで `y`/`n` により行う。挙動は `--approval` で制御でき、
一発実行(`polaris -p "..."`)と同じ意味を持つ。

履歴ペインは現時点でスクロールバックに対応していない。常に最新のメッセージを表示するのみで、
過去の履歴を遡って読むことはできない。この制限は把握したうえで本ブランチでは未実装のまま
見送っている。

### スラッシュコマンド

入力欄の先頭に `/` を打つと、一致するコマンドの予測変換ポップアップが入力欄の上に出る
(1文字打つごとに絞り込まれる)。`codex` の実際のピッカーと同じく、`↑`/`↓` でポップアップ内の
ハイライト(太字シアン、他の候補は灰色)を移動でき、Enterはそのとき**ハイライトされている行を
直接実行する**——コマンド名を最後まで打ち切る必要はない。もちろん最後まで打ってEnterでも動く
(その時点でポップアップの候補は1件だけになっており、それがハイライトされているため)。
実行されたコマンドは`polaris-tui`内で完結して処理され、モデルへは一切送られない
(`session.messages` にも追加されず、会話の永続化ファイルにも記録されない)——ただし`/compact`だけは
例外で、これはまさにこのコマンドの狙い通り、古い会話履歴をモデルへ送って要約させ、
`session.messages`を要約後の内容へ丸ごと置き換え、会話の永続化ファイルもその内容で書き換える。

| コマンド | 内容 |
| --- | --- |
| `/help` | 使えるコマンドの一覧をステータス行に表示する |
| `/status` | プロバイダ名・モデル名・累積トークン使用量・現在のメッセージ数を表示する |
| `/compact` | 古い会話履歴を1件の要約に置き換え、コンテキストの使用量を減らす(閾値超過時は自動でも走る)。モデルへ実際に送信する唯一のスラッシュコマンド |
| `/skills` | このプロジェクトで検出されたskillをフルスクリーンで一覧表示する(名前・説明、件数の上限なし) |
| `/new` | 今の会話は保存したまま、新しい会話を開始する(古い会話は `/resume` から後で戻れる) |
| `/resume` | 保存済みの会話から選んで再開する。起動元ディレクトリごとにグループ化され、
今いるディレクトリのグループが一番上に来る(下記参照) |
| `/clear` | この会話の履歴を消去する(永続化ファイルも空にする。`/new` と違い元に戻せない) |
| `/init` | カレントディレクトリに `AGENTS.md` の雛形を作成する(既に存在する場合は何もしない) |
| `/model` | 対話的なピッカーでモデルとreasoning effortを選び直し、以後のターンに即座に適用する |
| `/diff` | `git diff` の内容を会話履歴に表示する(200行を超える分は打ち切り、その旨を明示する) |
| `/review` | 現在の変更点をレビューしてほしい、という指示をモデルへ送る(`/review 認証周りを重点的に` のように追加の指示も付けられる) |
| `/permissions` | 承認ポリシー(`never`/`on request`/`always`)を対話的なピッカーで選び直し、以後のターンに適用する |
| `/fork` | 今の会話を新しい会話としてその場で複製する(元の会話はそのまま `/resume` から辿れる) |
| `/export` | 会話をmarkdownとしてファイルへ書き出す(`/export notes.md` のようにファイル名を指定できる。省略時は `polaris-export-<タイムスタンプ>.md`) |
| `/pwd` | 現在の作業ディレクトリを表示する |
| `/logout` | 保存済みのChatGPT資格情報(`~/.polaris/auth.json`)を削除する |
| `/quit` | polarisを終了する(`Ctrl-C`、`/exit` と同じ) |

`/model`・`/permissions`・`/skills` はいずれもフルスクリーンのピッカーを開く。codexの実際の
`/model` ピッカー(番号付き選択肢+`(current)` 表示+`↑`/`↓`+Enter確定/Esc戻る)のスクリーンショットを
確認したうえで、同じ見た目・操作感を採用した。`/model` はデスクトップスクリーンショットに写っていた
モデル名をそのまま候補として使う——ライブでモデル一覧を取得する仕組みは無いため固定リストである。

モデルを選ぶ(Enter)と、続けてreasoning effortを選ぶ2段階目の画面が開く(low/medium/high/extra
high/max/ultraの6段階、これもcodexの実際の"Select Reasoning Level"画面のスクリーンショット2枚を
確認して用意した表記)。codex側はmax/ultraだけ「More reasoning...」から別画面(Advanced
Reasoning)に分けているが、polarisでは1つのフラットな一覧にまとめて表示する(利用者からの明示的な
指示)。1段階目の`(default)`+`(current)`ラベルはlow行に固定で付き、加えて現在選択中のeffortにも
`(current)`が付く(同じ行なら`(default, current)`とまとめて表示)。効果側でEscを押すと2段階目
だけ戻ってモデル一覧へ(ウィザード全体は取り消さない)、モデル一覧側でEscを押すとウィザード全体を
取り消す——いずれもピッカー自身の"esc to go back"というヒント表記に合わせた。

選ぶと`polaris_provider::Provider`に新設した`set_model(&self, model: &str)`/
`set_effort(&self, effort: Option<&str>)`(いずれも内部可変性で実現し、既存の`&dyn Provider`参照
越しに呼べる)経由で実際に次のターンから送信されるモデル名・reasoning effortが切り替わる——実際の
HTTPリクエストのbodyが変わることをモックサーバーで確認済み(OpenAI互換プロバイダは
`reasoning_effort`フィールド、codexプロバイダは`reasoning.effort`——アカウントのプランから自動決定
される既定値を、`/model`での明示的な選択が上書きする)。footerにはモデル名の隣にeffortも表示される
(`gpt-5.6-sol high · ~/...`、これもスクリーンショットで確認した実際の表記)。

ピッカーの表示名(`"extra high"`など、空白を含む)は、そのままAPIへ送ると実際に拒否される
(`400 Invalid value: 'extra high'. Supported values are low, medium, high, xhigh.`という実エラーを
利用者が実際に踏んだ)。`polaris_auth::effort_for_plan_type`(既存)が既に`"low"`/`"xhigh"`という
空白なしのトークンだけを実際にAPIへ送る値として使っていたことを根拠に、`render::effort_wire_value`
(新設)で表示名→実際に送る値への変換を追加した——`"extra high"`は`"xhigh"`へ、`"max"`/`"ultra"`
(ChatGPTアプリ側だけの上位プラン向け表示で、API側にリテラルな受理値が存在するという根拠が無い)も
同じく`"xhigh"`へ落とす。footer・通知に表示される`effort_name`は引き続き表示名(`"extra high"`等)の
まま——実際に送る値だけが変わる。

`/permissions` は既に状態として持っている `ApprovalPolicy` に、`/skills`は発見済みのskill一覧に、
それぞれ同じピッカーの見た目を適用した(`/skills`はcodexと違い有効/無効の切り替え機能を持たないため、
Enter/Esc双方が単に閉じるだけの閲覧専用)。

`/resume` はフルスクリーンのピッカーを開く。`↑`/`↓` で移動、Enterで選択中の会話を読み込み、
Escでキャンセルする(スラッシュコマンドのポップアップと同じ操作感)。一覧は起動元ディレクトリごとに
グループ化され、各グループの見出しにはそのディレクトリの絶対パスを表示、今いるディレクトリの
グループが(古くても)常に先頭に来る。それ以外のグループは、そのディレクトリで最後に会話した
日時が新しい順に並ぶ。各行には開始日時の相対表記(`42s ago`/`35m ago`/`2h ago`/`3d ago`、30日を
超えると絶対日時表記に切り替わる)・メッセージ数・最初のユーザーメッセージのプレビュー(60文字で
打ち切り)を表示する。選択中の行は `❯` マーカーで示し、画面下部に `enter to resume · esc to cancel`
のヒント行を出す——相対時刻表記・マーカー・ヒント行はいずれもcodexの実物 `/resume` 相当ピッカー
(`resume_picker.rs`)を実際に読んで確認した表記を踏襲している(codex側はテーブル型のソート・検索
機能も持つが、polarisには対応する機能が無いためそこは対象外)。会話を選ぶと、以後の送信はその会話の
ファイルに続けて追記される——選ぶ前にいた(まだ何も送っていない)空の会話は、保存されていなければ
そのまま消える。

`codex` の実際のソースコード(`codex-rs/tui/src/slash_command.rs`、GitHubから取得して確認)には
約65個のスラッシュコマンドが定義されている。うちpolarisの既存アーキテクチャで完結する範囲
(17個)を実装した。`/diff`・`/review` は、`/` の候補が一致ゼロで消えるたびに「絞り込みが
壊れているのでは」と誤解されやすかった実装ギャップのうち、実際にcodexで使われている頻度が
高いものを優先して埋めた。`/review` だけは他と違い「ローカルで完結する処理」ではなく、レビュー
指示をモデルへの通常のユーザーメッセージとして送るプロンプト展開である(diffは既にモデルが
持つ`bash`/`read`から見える)。

残る約48個——`/mcp`・`/apps`・`/plugins`・`/vim`・`/keymap`・`/hooks`・`/import`・
`/memories`・`/theme`・`/pets`・`/ide`・`/plan`・`/goal`・`/agents`・`/subagents`・`/side`・
`/btw`・`/ps`・`/stop`・`/title`・`/statusline`・`/feedback`・`/personality`・`/experimental`・
`/approve`・`/mention`・`/copy`・`/usage`(`/status`のトークン表示と重複)・`/rename`・
`/archive`・`/delete`(タイトル/ライフサイクルという`/resume`側にまだ無い概念が要る)・`/cd`
(サンドボックスのルート解決と絡むため見送り)等——は、MCPクライアント・IDE連携・
マルチエージェント編成・バックグラウンド端末・端末ペットといった、polarisにまだ無い基盤を
要するため見送っている。

### 手で確かめる

自動テストは実端末を必要とする部分(画面描画・キー入力そのもの)を確認できない。
`polaris` を実行し、以下を目視で確認する。

- `POLARIS_API_KEY`/`~/.polaris/api_key.json`/`~/.polaris/auth.json` いずれも無い状態で `polaris` を実行すると、選択画面が出ること
- ↑/↓および1/2キーで選択が切り替わり、Enterで確定できること
- 「OpenAI APIキーを入力」を選ぶと入力欄が出て、入力した文字が伏字(`*`)で表示され、
  Enterで確定した後そのまま対話が始まること(再実行不要)。終了後 `~/.polaris/api_key.json` が
  作られていること
- 「ChatGPTでサインイン」を選ぶとブラウザが開き、認可完了後そのまま対話が始まること
  (`polaris login` と同じ経路であることの確認)
- 会話履歴と入力欄が表示され、文字入力・Backspace・Enterで送信できる
- 送信後 `thinking...` の表示を経て応答が履歴に追加される
- 書き込みを伴う指示(例:「test.txtというファイルを作って」)で承認モーダルが出て、
  `y`/`n` で応答できる
- `Ctrl-C` で終了し、`~/.polaris/state/<project-id>/tui-session.jsonl` が作られていること
- 同じディレクトリで再度 `polaris` を実行すると、直前の会話が履歴に表示されること
- ステータスバーにプロバイダー名・モデル名・トークン使用量(累計)が表示され、ターンが進むごとに数値が増えること
- ツールを使う指示(例:「Cargo.tomlを読んで」)で、履歴に `⚙ read(...)` と `→ ...` が表示されること
- `**太字**` を含む応答が太字で表示され、`` `コード` `` がバックティック無しで区別可能な見た目になること
