# 要求間隔とキャッシュ再利用の検証

v0.10.0 Algediの追加実験。`POLARIS_CACHE_PACING=on`で、同じCodex providerからのモデル要求開始を最低5秒間隔にする。本文・履歴・tools・モデル・推論強度は変えない。既定は`off`を維持する。実測は対照側の品質失敗で停止し、全比較の採用条件を判定できなかった。

## 仮説と動作

[公式キャッシュ文書](https://developers.openai.com/api/docs/guides/prompt-caching)では、毎分15要求を超える通信で、キャッシュを持たない処理先へ振り分けられる場合があると説明されている。前回の36ターン実測は60秒間に最大25〜26要求であった。送信を間隔化するとキャッシュ率が上がる可能性があるが、Codex backendへの適用や効果は未確認である。

onでは最初の要求を待たせず、その後は前回の要求開始から5秒が経過するまで待つ。応答に5秒以上かかった場合は追加で待たない。同じproviderを共有する並行要求にも適用する。待機中のキャンセルは送信済みとして数えず、既存の認証・再試行・timeoutの規則を維持する。

対象はCodex providerのモデルPOSTのみ。別プロセスや別providerの通信、サーバー全体の負荷を制御するものではない。キャッシュキーや会話単位のHTTPヘッダーも今回の比較では変更しない。

## 比較条件

`gpt-6-astra`、`medium`、`compact`、turn affinity offを固定する。[前回の品質行列](gpt6-cache-affinity-results.md#品質ケース)と同じdriver・問題文・正答条件を使い、同じ新規バイナリのpacing off/onを逐次比較する。過去の完了試行は新しい対照へ混ぜない。

まずL01/L02の36ターンを各条件1回、計4試行実行する。品質・変更範囲・使用量・実際の開始間隔を検査し、長期総量が対照の95〜105%内、課題別の増加が10%以内、キャッシュ率上昇・非キャッシュ入力低下・費用低下がすべて成立した場合だけ、修正課題30試行と短期18試行へ進む。

## 実測結果

2026-09-07、4試行を開始し3試行が完了。最後のL02 offは17ターン目の品質検査で停止した。実行した125ターンのうち124ターンが合格し、149モデル要求の使用量をすべて照合した。条件付きの短期18試行・修正30試行と、停止後の19ターンは実行していない。完了済み試行の再実行や追加の課金再試行は0。

### L02の停止と判定

skill 30個・tool 6個・few-shotのL02は、onが36ターン完了、offが17ターン目で停止した。offではformat-contract skillを取得して署名コードを回答する要求に対し、直前の会話内の値を再回答し、必要なskill呼び出しも行わなかった。通信は成功し、usageも記録されている。採点器の未対応構文ではなく、回答とツール使用の品質条件を満たさなかった。

比較元のoffが未完了なので、L02の費用・キャッシュ率をonと対比較しない。この失敗はpacingによる品質悪化を示すものではないが、事前に定めた全比較の品質条件は満たせず、採用を判断できない。既定offを維持し、pacingは任意の実験設定として残す。

onの2試行ともモデル要求は43回で、最小開始間隔は5,001ms／5,000ms、60秒間の最大要求数は12回だった。時間制御自体の実効性は確認できた。

### 失敗を含む消費量

全149要求の入力258,910、出力2,658、キャッシュ入力164,608、総261,568トークン。標準API換算は$1.240528。失敗したL02 offの20要求・28,577トークン・$0.166010も含む。全記録のモデル・推論強度・usage・変更範囲を照合し、usage欠測とcache writeは0だった。試行長が異なるため、この合計を条件間の性能比較には使わない。

換算は[GPT-6 Astraの標準API単価](https://developers.openai.com/api/docs/models/gpt-6-astra)の100万トークンあたり入力$10・キャッシュ入力$1・出力$50を使用した参考額。Codexでの実請求や利用枠消費を表すものではない。キャッシュキーは試行ごとに分離したが、backend上の完全な独立性やサーバー負荷の一致までは保証していない。

## 実装の検証

モデル要求の本文を組み立てた後、HTTP送信前にprovider単位で開始間隔を調整する。待機中に取り消された要求は将来の送信枠を残さず、モデル使用量の行にも数えない。診断ログは待機時間と送信後の経過時間を分け、単調時計による開始間隔を記録する。

回帰検証は全workspace 961件、実測driver 6件、Python 46件が成功。provider 123件には本文不変、並行要求の間隔、キャンセル後の再要求、401後の再試行、診断時刻とエラー分類を含む。fmt、全target clippy、filemap、差分検査も成功した。最初のprovider試験はモックのローカルポート権限で失敗し、必要な権限で再実行した結果を上記件数としている。
