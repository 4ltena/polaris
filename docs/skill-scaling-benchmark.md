# skill/pluginを大量に含めた比較

この測定は以前の版で記録したものであり、[GPT-6 medium実測結果](gpt6-efficiency-results.md)とはモデル、課題、測定時期が異なる。固定コンテキストの差を作業全体の削減率へ置き換えない。

## 方法

curatedリポジトリから831件（skill 646件、plugin 185件）を収集し、pluginは`name`と`description`をfrontmatterへ写した最小の`SKILL.md`として配置した。macOSの大文字小文字を区別しないファイルシステムで1件が衝突し、実際に設置したのは830件である。

同一の`reverse_string`実装とテスト作成課題を、830件を置いた`codex`、`pi`（`openai-codex/gpt-5.6-sol`）、Polaris（`POLARIS_PROVIDER=codex`）で各1回実行した。トークン数はAPI応答の`usage`、時間はプロセスの壁時計時間である。単回測定のため、反復時や別課題へ同じ差を一般化しない。

## 初回入力トークン

| skill数 | codex | pi | Polaris | pi/codex | Polaris/codex |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 30,612 | 1,195 | 547 | 3.9% | 1.79% |
| 5 | 31,464 | 1,822 | 547 | 5.8% | 1.74% |
| 830 | 44,292 | 110,692 | 547 | 249.9% | 1.23% |

Polarisの547は当時のAPI使用量であり、現在の固定コンテキストの測定値ではない。`lookup`を呼ばない3ターンの入力は547、600、747トークンで、skillを置かない場合と変わらなかった。`lookup`を呼ぶ場合のコストは、その呼び出しをしたターンにだけ加わる。

Codexはskill数が多いとき、descriptionを含む形式から短縮パスだけの形式へ切り替えるため、skill数に対する入力増加は一定ではなかった。piはこの種の圧縮を使わず、830件ではcodexの約2.5倍になった。5件と830件の2点だけから求めた交差点の推定は実測ではない。

候補の説明は先頭文を200バイトで表示し、831件の候補リストのレンダリングは43,777から20,389トークンへ下がった。最初の`lookup`の増分は1,234から624〜660トークンとなり、先頭8件だけ説明を残す変更後は344トークンになった。候補名は全件表示する。これらは評価用コーパスに対する記録であり、任意のskill集合での再現を保証しない。

## 時間

| 条件 | 所要時間 |
| --- | ---: |
| codex | 11.3秒 |
| pi | 13.3秒 |
| Polaris、`lookup`なし | 8.8秒 |
| Polaris、`lookup`を2回 | 13.9秒 |

この結果は1回の測定である。ネットワーク、サーバー負荷、検索内容の差を切り分けていないため、トークン数の差と同じ確度で速度を主張しない。
