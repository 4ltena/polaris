- 状態: M1〜M3b（`hamal`・`Aldebaran`）実装済み。M4（`Castor`）着手前に、実装済み部分との差分を本改訂で反映した

- 対象: `/Users/kn/File/projects/codex/polaris/`

## 概要

polaris は Rust で書くコーディングエージェントのハーネスである。常時コンテキストを 990 トークン以下に抑えたまま、subagent による並列実行を備え、対話型の日常ドライバとして Codex CLI を置き換える。

主張は二つに集約される。第一に、subagent の契約は呼び出しごとに書き下すのではなく型定義へ畳み込む。第二に、常時載せる文脈をツール定義と憲法に限り、それ以外はローカルのルータが必要な回だけ添付する。

## リリース方針

> この節は設計時点のものである。実際の運用はこれと異なる形に落ち着いた。差分をここに記す。

システム名は polaris であり、コンポーネントごとに星の名を付けたコードネームで呼ぶ。

設計時点では「`v1.0.0`（hamal）は M1 と M2 が両方完了した時点で付与する」としていたが、実際には M1・M2・M2.5（ChatGPT サブスクリプション認証）・M3a（skill 探索）がまとまった時点を核となる harness の区切りとし、`v0.1.0` を `hamal` として `81e11ad`（M3a 完了と英語化スイープの直後、M3b 着手前）へタグ付けした。M3b（BM25 ルータ、本書のルータ節が本来指していた機能の実装）以降は、核となる harness とは別系統の「skill/plugin 分類機」として `polaris-tools` 自身の crate バージョンで追う。`v0.2.0` を `Aldebaran` として、分類機がひととおりの最適化（`description_preview`、候補の階層化、`read` の出力上限）を終えた時点へタグ付けした。

M4（subagent・波・継続波）のコードネームは `Castor` とし、`v0.3.0` を予定する。

## 背景

ハーネス5種を同一モデルで比較した計測では、初回入力トークンに一桁の開きがある。Pi は 1,591 トークン、opencode は 7,155、qwen-code は 17,747、Claude Code は 19,048 であった。Pi が軽いのは、ツールを read・write・edit・bash の4本に絞り、システムプロンプトを数文に留めているためである。ただし Pi は subagent と plan mode を意図的に持たない。1,591 という値はオーケストレーションを捨てた対価でもある。

現行の Codex 環境は反対側に寄っている。`~/.codex/AGENTS.md` は 20,289 バイトあり、毎ターン載る。skills は15個で合計 237KB、その説明文がカタログとして提示される。

subagent の呼び出しコストも大きい。codex-orchestia では1体につきルートモデルが約 2,900 バイトを書き出す。内訳は manifest エントリが約 1,300 バイト（ネストを含めて29フィールド）、routing-facts が約 740 バイト、prompt ファイルが約 780 バイトである。30体を並べた実績では manifest 39KB、routing-facts 22KB、prompts 23KB の合計約 85KB をルートが生成していた。呼び出すための記述量が実行そのものを上回る。

## 設計目標

1. 常時コンテキストを 990 トークン以下に保ち、skill 数が増えても増加しない
2. subagent 1体あたりの呼び出し記述を 100 バイト以下に抑える
3. 権限の宣言と強制を同一のオブジェクトにし、両者が乖離しない
4. Agent Skills 仕様に準拠し、独自形式を作らない
5. サンドボックスを自作せず、実績のあるカーネル機構へ委譲する

## 非目標

- Codex CLI の全機能を再現すること
- サンドボックス機構そのものの実装
- クラウド実行、チーム共有、Web UI
- 初版でのプラグイン市場や配布基盤
- Windows 対応。サンドボックス強制の委譲先が macOS と Linux にしか無く、強制の無い環境で動かすと「カーネルレベルのサンドボックス」という看板が実態とずれる

## 全体構成

> この節は設計時点のものである。実装は 9 クレート固定という制約を自ら破り、7 クレートへ収束した。理由と現状を記す。

Cargo workspace とする。設計時点ではクレートを9個に固定し、増やすことを設計上の後退とみなしていたが、実装が進むにつれて2つの想定が崩れた。第一に、ルータ（BM25 とその周辺）は独立クレートを立てるほどの重さがなく、`polaris-tools::skill` のサブモジュール（`bm25.rs`、`near_universal.rs`）として収まった。第二に、ChatGPT サブスクリプション認証（M2.5）という設計時点に無かった要件が、独立クレート `polaris-auth` を要求した——`~/.codex/` の資格情報に一切触れないという不変条件を型で保証するには、他の何にも依存しない専用の store が要る。差し引きで「増やすことは後退」という原則そのものは変えず、実際に増えたクレート（`polaris-auth`）と、増やさずに済んだ機能（router）の両方について、その都度この判断を適用した結果が今の7クレートである。

| クレート | 責務 | 状態 |
| --- | --- | --- |
| `polaris-core` | エージェントループ、セッション、圧縮、監査ログ | 実装済み |
| `polaris-provider` | プロバイダ抽象 | 実装済み（フォールバック連鎖は未実装。エラー処理節に記す） |
| `polaris-tools` | 組込みツール（現在5本、`skill` の下にルータを内包） | 実装済み |
| `polaris-sandbox` | 方針の定義と OS 機構への委譲 | 実装済み |
| `polaris-skills` | Agent Skills のローダと検証 | 実装済み |
| `polaris-auth` | ChatGPT サブスクリプション認証の資格情報 store。設計時点には無かった | 実装済み（M2.5） |
| `polaris-cli` | バイナリ | 実装済み |
| `polaris-tui` | Ratatui による対話画面 | 未着手（M5） |

`polaris-router` という独立クレートは作らなかった。`polaris-agents`（subagent 型レジストリ、スケジューラ、波と継続波）も同じ判断に倣い、新設せず `polaris-core` へ置く——`polaris-core` は既にエージェントループとセッションを持ち、subagent のオーケストレーションはその自然な延長にあたる。`spawn` ツール自体は他のツールと同じく `polaris-tools` に置く。

「ルータは `polaris-sandbox` にも `polaris-agents` の権限にも依存しない」という設計時点の不変条件は、独立クレートによるコンパイラ強制ではなく、モジュール単位の規律として引き継ぐ。`polaris-tools::skill` 以下のモジュール（`bm25.rs`、`near_universal.rs`）は `polaris_skills::Skill` 以外の何にも依存しない——`polaris-sandbox` や `polaris-core` の型を一切 import しない。これはクレート境界による保証より弱い（コンパイラは違反を止めない）が、`polaris-tools` 全体のうち、書込系ツール（`write`・`edit`）だけが `polaris-sandbox` を要し、skill のモジュール群はそもそも要求する理由がないため、規律が崩れる動機自体が薄い。

## 常時コンテキスト予算

> この節は設計時点の見積で、その後の実測で二度更新されている（M3a 時点、そして本改訂）。数値の出所は必ず添える。

設計時点の見積表（システムプロンプト 250、各ツール合計、`spawn` を含めて 875）は、M3a 完了時点の実測（下限 267、真の同時最大 626）で既に大きく訂正されていた。その後、`crates/` 配下の日本語コメント・エラーメッセージ・ツールスキーマを英語へ翻訳したこと（見積ではなく tiktoken が英語をより少ないトークン数へ符号化する実測上の効果）と、M3b（BM25 ルータ）でツールが1本（`skill`）増えたことで、数値はさらに動いた。

M3b 完了時点、ツール 5 本（`read`・`write`・`edit`・`bash`・`skill`）を載せた実測値は、システムプロンプトとツール定義だけの下限が 496 トークン、憲法と環境情報を同時に上限まで充填し skill 100 件を与えた真の同時最大が 855 トークンである。ツールごとの内訳（実測、o200k_base）は `read` 69、`write` 76、`edit` 115、`bash` 69、`skill` 89。

`spawn`（M4）を仕様書どおりの呼び出し形（`spawn([{type, task}, ...]`）に沿ったスキーマで追加し、同じ条件で測ると、6 本目を加えた真の同時最大は **798 トークン**——上限 990 に対して 192 の余裕がある。M2 の最終レビューが指摘し、M3b の繰り越しとして「6 本目のツールと予算の衝突は M4 の仕様で決める」と記録されていた懸念は、その指摘の時点（`edit` のスキーマが 136 トークンだった頃）を基準にしたもので、英語化を経た現在の実測ではもう成立しない。この節の訂正がその答えである。

数値を書くときは、それを産んだテスト名を添えること。下限は `budget.rs` の `always_on_context_stays_within_budget`、真の同時最大は `constitution.rs` の `absurdly_long_cwd_cannot_push_the_assembled_system_over_budget` が測っている。`spawn` を含めた 798 トークンは、同じ2つのテストの手法をこの改訂のために一時的に再現して測った値であり、`spawn` 自体がまだ実装されていないため常設のテストはまだ無い——M4 実装時に `budget.rs` へ加える。出所の無い数字は書いた時点から腐る。

skill の追加によって合計は変化しない。ルータが発見を担うため、skill 名の一覧を常時載せる必要がないからである（`budget.rs` の `near_universal_skills_do_not_move_the_always_on_total` が、ルータが選ぶ候補の有無・件数によっても変化しないことまで固定している）。

`write` を `edit` へ統合すれば数十トークン削減できるが採用しない。編集は最も高頻度かつ失敗が痛い経路であり、トークンと引き換えに信頼性を賭ける取引は成立しない。

見積の誤差は2割を見込む。数値は測定で担保する。詳細はテスト戦略に記す。

## ツール

常時提供するツールは6本で固定する。

- `read` ファイル読み取り
- `write` 新規作成
- `edit` 既存ファイルの部分置換
- `bash` シェル実行
- `skill` skill の検索と読み込み
- `spawn` subagent の起動

`grep` と `find` は `bash` 経由とし、独立したツールにしない。MCP サーバのツールも常時展開せず、`skill` 経由の遅延接続とする。機能追加は例外なく `skill` と `spawn` の背後に置く。

## Skills

Agent Skills 仕様にそのまま準拠する。独自のフロントマターを追加しない。

`name` は 64 文字以内、小文字英数字とハイフンのみ、先頭と末尾にハイフンを置かず、連続ハイフンを含まず、親ディレクトリ名と一致する。`description` は 1024 文字以内。任意フィールドとして `license`、`compatibility`、`metadata`、`allowed-tools` を受け付ける。

探索順は次のとおりとする。名前が衝突した場合は先に見つかったものを採用する。

1. `<project-root>/.polaris/skills/`
2. `~/.polaris/skills/`
3. 設定ファイルの `skills.paths` に列挙された場所

設定ファイルは `~/.polaris/config.toml` と `<project-root>/.polaris/config.toml` の 2 つで、後者が前者を上書きする。tier とモデルの対応もここに書く。

起動時と CI で `skills-ref validate` にかけ、仕様違反を検出する。

## ルータ（M3b で実装。設計時点との差分が大きいので全面的に書き直す）

> 設計時点のルータは「モデルの往復そのものを無くす、メッセージ末尾への自動差し込み」を主目的としていた。M3b で実際に作られたのは、往復（`skill` ツールの呼び出しと結果読み取り）は残したまま、その1回分の検索精度とコストを最適化する仕組みである。目的そのものが変わったので、以下は実装済みの姿として書く。設計時点の版は git 履歴に残る。

`polaris-tools::skill::lookup` として実装済み。モデルが `skill` ツールを呼ぶと、名前完全一致なら該当 skill の本文を、そうでなければランキング済みの候補一覧を返す。

### 実際に採った形と、設計時点との違い

往復自体を無くす「メッセージ末尾への自動差し込み」は実装していない。理由は2つある。第一に、`skill` ツールへの応答はもとよりメッセージ末尾（会話履歴の末尾に積まれるツール結果）に入るため、システムプロンプトやツール定義という「キャッシュの接頭辞」には最初から触れない——設計時点が懸念していたキャッシュ破棄は、自動差し込みという仕組みを持ち込まなくても既に起きていなかった。第二に、モデルが明示的に検索した回だけコストを払う往復型のほうが、常時コンテキストを skill 数から独立させるという設計目標そのものと相性が良い。自動差し込みは「モデルが求めていない skill まで毎ターン届く」経路を作りかねず、この点は `docs/superpowers/CURRENT.md` の M3b 繰り越しでも懸念として記録されていた。

段階構成も変わった。第一段は語彙検索（バイグラムではなく BM25、英語トークンへの語幹化と同義語展開つき、name フィールドを3倍重みで加算）で上限20件まで絞る。設計時点の「8件」ではなく `MAX_RESULTS = 20` を採用したのは、recall の実測（831件の実コーパス、132件の評価クエリで測定）で 8〜10 件では recall が大きく落ちる一方、20件は「検索1回で一望できる規模」という設計目標とまだ両立したためである。

日本語の扱いは「文字バイグラムで索引する」という設計時点の方針を採らなかった。BM25 のトークナイザは ASCII のみを対象とし、日本語クエリのように BM25 が0件しか返さない場合は、旧来の部分文字列一致へフォールバックする。これは BM25 化によって日本語の検索性を悪化させないための保険であり、バイグラム索引によって日本語の検索精度そのものを上げる設計とは別物である。

第二段の「超小型分類モデル」は実装していない。代わりに `near_universal` という、モデルではなく機械的な規則（trigger 形式の description・量化語・固有の技術名の有無）で選ぶ、少数の「ほぼ常に関連する」skill の集合を、検索結果に常に追加する。第一段の語彙検索が原理的に見落とす種類の候補（クエリの語彙とは一致しないが、タスクの局面によって常に関連する skill）を拾う点は設計時点の意図と同じだが、分類モデルではなく description の書き方の慣習を機械的に検出する点が違う——推論時に LLM を呼ばないという制約（オフライン学習のみ）を守ったまま実装できる形を選んだ結果である。

トークンコストを抑えるため、候補一覧は各候補の description を全文ではなく先頭文（`description_preview`、200 バイト上限）だけ表示し、さらに並び順の先頭 `MAX_PREVIEWED_RESULTS`（8）件だけをプレビュー付き、残りは名前のみで表示する（`MAX_RESULTS` 自体は減らさない）。これは設計時点には無かった最適化で、詳細は README.md「skill/plugin を大量に含めた場合の比較」に実測とともに記す。

### 不変条件（設計時点のまま維持）

1. ルータは減算の権限を持たない。憲法ブロック、ツール定義、サンドボックス方針、承認境界のいずれにも触れられない。誤動作しても失われるのは添付されなかった skill だけであり、安全規則は落ちない
2. 出力は検証済み skill 名の集合に限る。自由文を生成させない
3. ローカルで実行する。推論時に外部 API（LLM を含む）を呼ばない

3番目は設計時点より厳格化されている。設計時点は「外部 API に依存させない」とだけ書いていたが、実装ではローカルの LLM 推論も含めて禁じた——オフライン学習のみで完結させ、ランタイムは軽量な決定的アルゴリズムに留める、という制約を明示的に固めた。

### 評価指標（実測値）

実コーパス831件（skill 646・plugin 185）と、22の実プロジェクトから生成した132件の評価クエリで測定した。

- BM25 単体（語幹化・同義語展開・name 重み付けをチューニング後）: recall 74%（50件中37件）
- BM25 + near_universal: recall 98%（50件中49件）
- 常時コンテキストへの影響: ゼロ（`budget.rs` の不変条件テストで固定）。skill を1件も置かない状態と 830 件設置した状態とで、実 API 応答の入力トークン数が完全に一致することを実行して確認した
- 検索1回あたりの実測コスト: 830件コーパスに対する `lookup` 呼び出し1回目の増分で、当初の最適化前1,234トークンから、先頭文プレビューと階層化を経て344トークンまで下がった（約72%減）

キャッシュヒット率（ルータの有無で変化しないこと）は未計測のまま残っている——`docs/superpowers/CURRENT.md`「次の一手」に記録済みの繰り越しで、タグ準備の前に測る計画である。

### M4 subagent 型discoveryとの関係

subagent の型定義は Agent Skills 準拠のディレクトリ（`agents/` 配下）に置く設計であり、skill と同じ形式である。型の一覧が増えたときに同じ「常時コンテキストへ静的カタログとして漏れる」問題を再び抱えないよう、subagent 型の discovery はこのルータの仕組み（`polaris_tools::skill::lookup` と同じパターン、必要なら同じ実装）をそのまま流用する。新しい discovery 機構を M4 で別途作らない。

## subagent 契約

### 型定義

subagent の型は Agent Skills 準拠のディレクトリとして `agents/` 配下に置く。

```markdown
agents/file-inspector/SKILL.md
---
name: file-inspector
description: 単一ファイルを読み取り専用で棚卸しし、責務、入出力、対応するテストを返す。
allowed-tools: read
metadata:
  polaris-access: read
  polaris-tier: low
  polaris-wall-seconds: "360"
  polaris-max-turns: "12"
  polaris-continuation: "denied"
  polaris-output: references/result.schema.json
---

本文がそのまま subagent のシステムプロンプトとなる。
```

`allowed-tools` は仕様の実験的フィールドであり、事前承認されたツールを空白区切りで並べる用途に合致する。`metadata` は文字列から文字列への写像と規定されているため、数値も引用符付きで書く。キー名の衝突を避ける推奨に従い `polaris-` を前置する。

`agents/` は `.polaris/skills/` と同じ Agent Skills 形式であるため、型の discovery（一覧化・検索）にはルータ節に記した `polaris_tools::skill::lookup` のパターンをそのまま流用する。新しい discovery 機構を M4 のために別途作らない——探索順や `name`/`description` の検証規則も Skills 節のものを踏襲する。

### 呼び出し

```
spawn([
  {"type": "file-inspector", "task": "crates/polaris-core/src/loop.rs"},
  {"type": "file-inspector", "task": "crates/polaris-tools/src/skill/bm25.rs"}
])
```

配列を受け取り、並列に実行し、全件の完了後に結果配列を返す。1タスクあたりの記述は約60バイトである。30体で約1.8KB となり、現行の85KBに対して98パーセントの削減となる。

### フィールドの行き先

| 分類 | 例 | 行き先 |
| --- | --- | --- |
| 呼び出しで変わらない | kind、tier、access、prohibited_paths、side_effects、timeouts、retry_policy、出力スキーマ | 型定義 |
| ホストが決める | id、workspace、prompt のハッシュ、status、routing_reason | ランタイム |
| 呼び出しで変わる | 対象、書込先 | `spawn` の引数 |

## オーケストレーション

### 波

依存関係は有向グラフではなく波で表す。1波目の結果を読んでから2波目を起動する。`join` に相当するツールもハンドルも導入しない。

バリアであるため最も遅いタスクが波を止める。この損失は壁時計時間に限られ、トークンとターンには及ばない。単一の波ではどのみち全件の完了まで親は進めないため、損失はない。

### 継続波

素性の分かったパイプラインでは、子が結果とともに後続タスクの一覧を返し、ランタイムが同じ `spawn` 呼び出しの中で展開する。

深さ2の subagent と異なり、子は終了してから後続が始まる。子がスロットを保持しないため、待機中の親でプールが埋まる枯渇が原理的に起きない。子は `spawn` を持たず、返すのは検証済み型の一覧に限られるため、権限も広がらない。

親の往復が消えることで、多段作業の壁時計時間が縮む。10件2段の作業では、検査30秒、親の思考30秒、検証15秒の合計75秒が、各件の検査と検証の合計の最大値である約40秒になる。

歯止めを4つ置く。

M4 の初期実装では機構そのものを作るところまでとし、オプトインする型は0のまま出荷する。効果を主張できる実測（上記75秒→40秒のような具体例）が揃った型から個別に有効化する。

1. 型ごとのオプトインとし、既定は無効とする
2. 連鎖の上限を2回とし、それ以上は親へ返す
3. 1回の `spawn` 呼び出しあたりの総タスク数に上限を設ける
4. 書込先の衝突検査を全連鎖にわたって再実行する

### 深さ

深さ1で固定する。いずれの型も `allowed-tools` に `spawn` を含めない。動的な分割は継続波で扱う。

型定義の記述だけに頼らず、ランタイム側でも `spawn` を subagent の利用可能ツールから常に除外する。`allowed-tools` に書き忘れであれ誤ってであれ `spawn` が入っていても、subagent へ渡すツール一覧の構築側で無条件に落とすため、コンパイラ強制ではないにせよ規律違反1点に依存しない。

### 並列度

既定で同時8、うち書込4とする。設定可能とし、初期値は測定で見直す。インプロセスでは律速がプロバイダのレート制限にあるため、CPU 数を根拠にしない。

### 階層とモデル

型が宣言する `polaris-tier` を、設定がプロバイダとモデルへ割り当てる。

M4 の初期実装では、全階層を既存プロバイダ（`openai`・`codex`）の範囲で賄う。`ollama` 等のローカルモデルプロバイダは新規実装が要る別種の作業であり、M4（subagent/波/継続波）のスコープには含めない。低階層をローカルモデルへ逃がしてリモートのレート制限を消費しない、という以下の効果は将来の拡張点として設計だけ残す。

```toml
[tier.low]
provider = "codex"

[tier.medium]
provider = "openai"

[tier.ultra]
provider = "codex"
```

（将来、ローカルモデルプロバイダを実装した場合の例）

```toml
[tier.low]
provider = "ollama"
model = "qwen3-coder-30b"
```

低い階層をローカルモデルへ逃がすと、その分はリモートのレート制限を消費しない。実効的な同時実行数はリモートとローカルの上限の和になる。M4 の初期実装ではこの効果自体は得られず、階層は「同じプロバイダ内でのモデル選択」の意味にとどまる。

### 結果

型が宣言した出力スキーマでランタイムが検証する。不一致の場合は検証エラーを添えて1回だけ再試行し、なお不一致であればそのタスクのみ失敗記録を返す。波は停止しない。

subagent の中間過程は親のコンテキストへ入れない。12ターンを費やした subagent が内部で4万トークンを使っても、親が受け取るのは検証済みの結果のみである。

## サンドボックスと承認

`sandbox_mode` が技術的境界を、`approval_policy` が停止して確認する条件を定める。二つは直交する。

`sandbox_mode` は `read-only`、`workspace-write`、`full-access` の3値をとる。強制は macOS では実行時に生成した Seatbelt プロファイルを `/usr/bin/sandbox-exec` へ渡し、Linux では `landlock` クレートの ruleset を子の `pre_exec` の中で `restrict_self()` する。両者は共通の抽象を持たず、プラットフォームごとに明示的な実装を置く。一つの API で異なる保証を覆うことは、二つの実装を持つことより悪い。`polaris-sandbox` は方針と書込可能ルートのみを保持する。

いずれの機構もプロセス境界を越えてはじめて効く。既に起動して複数スレッドを持つプロセスへ後から健全に適用することはできない。したがって**ファイルシステムへの変更はすべてサンドボックス境界を越える**。`bash` はもとより、`write` と `edit` も、拘束モードで再実行した polaris 自身のバイナリが実際の変更を行う。`full-access` であっても境界を越える。試験する経路と本番の経路を同一に保つためである。

再実行するバイナリは書込可能ルートの外に置く。`current_exe()` は通常ビルド生成物の中にあり、ワークスペースへ書ける者がそれを差し替えれば、次の変更操作が差し替えられたコードを拘束下で実行してしまう。M4 の `read write` 型 subagent にとって、これは親より強い権限を得る経路そのものになる。

書込可能ルートと対象パスは、方針を組み立てる前に正規化する。経路の途中にシンボリックリンクがあると強制側は全てを拒否し、その拒否は方針違反と区別がつかない。macOS の `/tmp` と `/var` が該当するため、これは端の事例ではない。

強制が**適用に失敗した状態**は、拒否とは別の事象として扱い、必ず硬い失敗にする。入れ子や仮想化された環境では適用自体が失敗しうる。適用の失敗を拒否として扱うと、守っていない状態が守っている状態と同じ見た目になる。

停止して承認を求めるかどうかの判断には、拒否を事前に予測するプロセス内の述語が要る。述語は助言であって強制ではない。強制側は理由を説明できないためである。親ディレクトリが存在しない拒否は `ENOENT` を返し、`EACCES` は Linux では拒否だが macOS では通常の失敗であるから、errno による分類は成立しない。述語と強制は必ず食い違うので、固定のパス集合に対して両者を突き合わせる差分テストを置き、食い違いを既知の一覧として管理する。

subagent の実効権限は、型の `allowed-tools` と親の現在権限の積とする。subagent が親より強い権限を得る経路は存在しない。

`spawn` の引数で宣言した書込先が、そのタスクの書込可能ルートとなる。宣言と強制が同一のオブジェクトであるため、両者が乖離しない。同一の波で書込先が重なる場合は、1件も起動せずに `spawn` 全体を拒否する。部分的に実行された状態を残さないためである。

サンドボックスを超える操作の扱いは、事前に判定できるかどうかで分ける。`write` と `edit` は対象パスが一つに定まるため、述語で予測し、越えるなら実行前に停止して承認を求める。`bash` は任意のコードを実行するので、何に触れるかを事前に決定できない。試行し、拒否されたらモデルへ理由を返す。エラー処理の節が定める拒否メッセージはこの経路のためにある。

## コンテキスト圧縮

圧縮は履歴を書き換えるため、プロンプトキャッシュを必ず破棄する。剪定も書き換えであるから同じく破棄する。したがって剪定と要約を1回の操作にまとめ、閾値を高く置いて回数を最小化する。

閾値は有効窓の88パーセントとする。有効窓は文脈窓から最大出力トークンと安全余裕を差し引いた値である。

閾値の選び方には二つの力が働く。高くすれば圧縮の回数が減り、キャッシュの破棄も減る。低くすれば作業の途中で窓が尽きる事故を避けられる。Claude Code の95パーセントは前者に寄りすぎており、利用者からは遅すぎるとの報告がある。88パーセントはその中間にあたる。

さらに、この設計では subagent が探索を結果へ畳むため親の文脈が伸びにくい。88パーセントでも圧縮の発火頻度は他のハーネスより低くなる見込みであり、回数を抑える目的と事故を避ける目的が両立する。

| 扱い | 対象 |
| --- | --- |
| 触れない | 憲法ブロック、ツール定義 |
| 原文で残す | ユーザーメッセージのすべて |
| 原文で残す | 直近 40,000 トークン相当のツール出力 |
| 要約する | 古い応答とツール出力 |

> `ルータが添付した skill 本文を最初に捨てる`という専用の優先順位は設計時点の案であり、削除した。ルータ節に記した通りメッセージ末尾への自動注入は実装しておらず、skill 本文はモデルが `skill` ツールを呼んだ結果としてのみ文脈に入る——他のツール出力と区別する特別な経路がない。したがって skill 本文は上表の「古い応答とツール出力」と同じ扱いで十分であり、再取得したければモデルが `skill` を呼び直せる点も他のツール結果と変わらない。

## エラー処理

### プロバイダ障害

subagent ではフォールバック連鎖を有効にする。タスクが有界であり、出力がスキーマ検証されるため、応答した主体よりも契約への適合が問題となる。

ルートでは既定で無効とし、利用者へ確認する。セッションの途中でモデルが替わると振る舞いが変わり、キャッシュも失われる。

> フォールバック連鎖はまだコードとして存在しない（`polaris-provider` の `Provider::complete` はプロバイダ1本を1回叩くのみで、リトライも切替もしない）。M4 初期実装ではこの節が指す連鎖そのものを新設せず、subagent のプロバイダ障害は現在のルートと同じ「1回叩いて失敗ならそのまま失敗」を踏襲する。ただし結果節が定める通り、その失敗はタスク単体の失敗記録に留め、波は止めない。フォールバック連鎖の実装は、`ollama` 等ローカルプロバイダの追加と同様、M4 のスコープ外として残す。

### サンドボックス拒否

拒否を例外として扱わず、モデルが理解できる形で返す。拒否されたパス、現在の方針、書込可能ルートを含める。原因を掴めない拒否メッセージは同じ失敗の反復を招き、時間とトークンを消費する。

### 停止条件

同一のエラーが3回続いた場合に停止する。ルートと subagent の双方に適用する。加えて subagent には `polaris-wall-seconds` と `polaris-max-turns` の超過、出力スキーマの不一致2回を停止条件とする。

自動修復は実行しない。失敗は失敗として返し、判断をルートへ戻す。

### クラッシュ

セッションは追記専用の JSONL として保存する。異常終了で失われるのは進行中の1ターンに限られ、ディスクから再開する。

## 監査

追記専用の JSONL に、ツール呼び出し1回を1行として記録する。型、解決後のサンドボックス方針、書込先、結果を含める。監査は subagent に限らず全ツール呼び出しを対象とするため、`polaris-agents` ではなく `polaris-core` に置く。

記録する文字列は、書く直前に必ずシークレット伏字化を通す。`bash` のコマンド文字列を残す以上、生の資格情報がログへ落ちる経路を塞ぐ必要がある。

暗号学的な receipt は付けない。インプロセスでは署名する主体と行為する主体が同一であり、署名はログ以上のことを証明しない。署名が意味を持つのは検証者が別主体である場合であり、この構成は該当しない。

## テスト戦略

### 予算

実際のシステムプロンプトと実際にシリアライズされたツールスキーマを、本番と同じトークナイザで計測する。

- 合計が 990 を超えたら失敗する
- ツール本数が6を超えたら失敗する
- skill を15件から100件へ増やしても合計が変化しないことを確認する

### 安全性の不変条件

- いずれの型も `allowed-tools` に `spawn` を含まない
- subagent の実効権限が親の権限の部分集合である。全型と全親状態の組み合わせで検証する
- 同一の波で書込先が重なる場合、1件も起動せずに拒否される。継続波で新たに宣言された書込先を含めて再検査する
- ルータの出力によらず、憲法ブロックとツール定義がバイト単位で不変である
- キャッシュ接頭辞がルータの有無でバイト単位で一致する
- 宣言外への書き込みが実際のサンドボックスで拒否される。モックを用いず、書き込みを試みて拒否を確認する

### 回帰

固定タスク集に対して、成功率、トークン数、ターン数、壁時計時間を毎回記録する。

### 保証しない範囲

Seatbelt と landlock に迂回路が存在しないことは検証できない。上流の安全性をそのまま継承する。自作を避けて委譲する判断はこの限界を前提としている。

**書込可能ルートの内側に、外側を指す既存のハードリンクがある場合、そのリンク経由の書き込みは拒否されない。** 実測で確認している。両機構ともパスに対して判定するのであって、inode に対して判定しないためである。モデル自身が作ったリンクは `bash` の拒否で防げるが、pnpm や Nix のストアのように、モデルが関与せずに存在するリンクは防げない。述語側で `st_nlink > 1` を検出して承認へ回すが、これは緩和であって保証ではない。

## 受け入れ基準

1. 常時コンテキストが 990 トークン以下である。この上限は、ディスクから読む入力の大きさに左右されない。skill の数、AGENTS.md の大きさ、環境情報の長さのいずれが増えても、上限を超える経路が存在しないこと
2. subagent 1体あたりの呼び出し記述が 100 バイト以下である
3. 宣言した書込可能ルートの外を指すパスへの書き込みが、実サンドボックスで拒否される。モックを用いず、`write` ツールを通して書き込みを試み、拒否を観測する。共有の起動ヘルパを直接叩く経路では確認したことにならない。既存のハードリンク経由の書き込みはこの基準の対象外であり、保証しない範囲に記した
4. ルータの有無でキャッシュ接頭辞が一致する
5. 固定タスク集の成功率が Codex CLI を下回らない
6. 同一タスクのターン数が Codex CLI を上回らない
