# polaris skill ルータ BM25 化 設計

> M3b（BM25 ルータと評価コーパス）の設計。`docs/superpowers/CURRENT.md` の
> M3b 繰り越しに対応する。

## 目的

`polaris-tools::skill::lookup` の検索経路を、部分文字列一致から BM25 ラ
ンキングへ置き換える。あわせて、ごく少数の「ほぼ常に関連する」skill を、
検索クエリの一致に関係なく `lookup` の結果へ常時含める仕組みを足す。

## 前提と根拠

セッション内で Python によるオフライン評価を先行させた。831 件の skill/
plugin コーパス（codex 側の curated リポジトリからローカルに収集し重複
排除したもの）と、22 プロジェクトから生成した 132 件の自然文検索クエリ、
それぞれの正解 skill 一覧を用意し、複数の候補アルゴリズムを同じ正解に対
して測定した。

現行の部分文字列一致は、クエリ全体が name か description のどちらかへ
連続した部分文字列として現れることを要求する。実際に人が書くクエリは複
数語にまたがるため、132 件中すべてで一致件数 0 だった。

BM25（k1=1.5、b=0.75、name フィールドを 3 倍の重みで加算、軽量な接尾辞
除去による語幹化、一般的なソフトウェア開発用語の同義語展開）まで積み上
げたところ、上限 20 件のランキングで recall 74%（50 件中 37 件）まで伸
びた。ローカル埋め込みベクトル検索も試したが、BM25 を下回った。

残る取りこぼしを個別に確認すると、test-driven-development や
systematic-debugging のような「ほぼどんなタスクにも関連する」プロセス系
skill が大半を占めていた。これらは trigger 形式の description（`Use
when/for/before` で始まる）を持つ skill 全体を対象に、タスクの局面（実
装中・デバッグ中・検証前など）をタグ付けして候補を広げる方式も試したが、
候補プールが平均 40〜65 件に膨らみ、しかも語彙的なランキングでは正解が
その中に埋もれたままだった。プールを絞っても同じ天井（recall 76%）にぶ
つかった。取りこぼしの原因は、これらの skill がクエリの語彙と一致しない
ことそのものではなく、「このタスクに効く汎用プロセス skill はどれか」と
いう判断が語彙的手法の外側にあるためだと分かった。

そこで、機械的に選べる基準（trigger 形式の description、量化語
`any`/`every`/`all` を含む、固有の製品・技術名を含まない）で候補を絞る
と、831 件中 4 件だけが残った。これらをクエリに関係なく常に候補へ含める
と、recall は 98%（50 件中 49 件）まで伸びる。4 件の name と description
を合わせても 130 トークンで、`MAX_RESULTS` の枠を消費する追加候補として
見ても許容できる規模である。

測定に使ったコーパス・クエリ・正解データはこのリポジトリの外
（`/private/tmp/claude-501/.../scratchpad/`）にあり、本番のコードには含
めない。この設計はそこで得た比率と閾値（k1、b、name 重み 3、量化語リス
ト、同義語表）を移植するが、数値そのものは Rust 側で別のテストコーパス
により再検証する（受け入れ基準を参照）。

### 常時コンテキストへは置かない

`docs/superpowers/CURRENT.md` の「決めたこと」は次を既に定めている。

> 常時コンテキストは skill 数から独立させる。発見はローカルのルータが担
> い、skill 名の一覧を常時載せない
>
> ルータは加算のみで、憲法ブロック、ツール定義、サンドボックス方針、承
> 認境界には触れられない

セッション内の検討では、この 4 件を `assemble_always_on` のシステムプロ
ンプトへ焼き込む案も測定したが、この決定と正面から矛盾する。トークン数
が小さいこと（+130）は理由にならない。`budget.rs` が守る不変条件は「skill
数に依存しない」という性質そのものであり、閾値を満たす限り増えないとい
う条件付きの主張へ弱めることは、この不変条件を検出可能な形からまた検出
可能な形へ後退させるだけになる。加えて、常時コンテキストの真の同時最大
は現在 855/990 トークンで、M4 が繰り越している 6 本目のツール追加が既に
この余白を必要としている。ここへさらに恒常的なトークンを足す理由がない。

代わりに、この 4 件は `lookup` 自身の戻り値へ、クエリの一致とは無関係に
常時含める。`lookup` の呼び出しはツール結果としてメッセージの末尾に積ま
れるものであり、システムプロンプトの接頭辞には触れない。これは「ルータ
は加算のみ」という既存の決定にそのまま従う形であり、`budget.rs` 側の不
変条件・テストは一切変更しない。

この方式は、エージェントが一度も `skill` ツールを呼ばないターンでは 4
件も含めて何も見えない。これは既存の設計がそもそも持っている性質（ルー
タは呼ばれて初めて働く）であり、この変更が新たに持ち込むものではない。

## 非目標

- CJK（日本語等）テキストのトークン化。BM25 のトークナイザは
  `[a-z0-9]+` 相当の ASCII/ラテン文字のみを対象とする。この設計では、
  BM25 のランキング結果が 0 件のとき（日本語クエリを含む、トークンが一
  つも一致しないケース全般）に既存の部分文字列一致へフォールバックする
  実装を採用し、悪化させないという当初の目標を上回って、日本語
  description に対する既存の検索性を維持した。BM25 自身にトークナイザを
  拡張する対応は別の設計で扱う。
- 埋め込みベクトル検索。測定の結果、チューニング済み BM25 を下回った。
- 推論時に LLM を呼び出す判定。オフライン学習のみで完結させるという制約
  は今回の設計全体を貫く前提であり、ランタイムはローカルの軽量アルゴリ
  ズムに留める。
- `MAX_RESULTS`（20）を超える拡大。緩めた場合の recall 上振れ（30〜40 件
  で 76%）は小さく、コストに見合わない。
- 「ほぼ常に関連する」候補の選定基準を、このコーパス固有の skill 名に紐
  づける形にすること。基準は description の書き方の慣習（trigger 形式、
  量化語、固有名詞の有無）のみに依存し、新規に追加される skill が同じ慣
  習で書かれていれば、コード変更なしに同じ扱いを受ける。

## 構成

### `polaris-tools::skill`

既存の `MAX_BODY_BYTES` / `MAX_RESULTS` / `MAX_LIST_BYTES` /
`MAX_ECHOED_QUERY_BYTES` は変更しない。名前完全一致で body を返す経路、
空クエリで一覧を返す経路もそのまま残す。変わるのは検索（部分一致）の内
部実装だけである。

#### BM25 ランキング

- トークナイザ: 小文字化した上で `[a-z0-9]+` を抽出。英語の一般的なスト
  ップワードを除去。長さ 4 以下のトークンはそのまま、それより長いトー
  クンには軽量な接尾辞除去（`ies→y`、`ing`/`ed`/`es`/`s` を除去、除去後
  の長さが 3 未満になる場合は除去しない）を適用する。
- ドキュメント化: skill ごとに、name（`-`/`_`/`:` を空白に置換したもの）
  のトークン列を 3 回連結し、description のトークン列を続ける。
- スコアリング: 標準的な BM25（k1=1.5、b=0.75）。IDF はコーパス全体（渡
  された `&[Skill]` 全体）から `lookup` 呼び出しのたびに算出する。skill
  数は数百〜千のオーダーであり、この規模なら毎回組み立てても、`lookup`
  呼び出しの前に必ず挟まるモデルとの往復（数百ミリ秒〜数秒）に比べて無
  視できるという判断で、呼び出しをまたいだキャッシュは持たない。この判
  断自体をこのブランチで計測したベンチマークはない。状態を持たない現行
  の関数シグネチャ（`fn lookup(skills: &[Skill], q: &str) -> String`）を
  そのまま維持する。
- 同義語展開: クエリのトークンを、固定の一般的なソフトウェア開発用語の
  同義語表と照合し、一致したものがあれば同義語をクエリへ追記してからス
  コアリングする。表はこのコーパスの skill 名を含まない、用語同士の対応
  のみで構成する。

  ```
  credential   -> secret, key, token, password
  leak         -> expose, exfiltrate, commit, leaked
  403          -> forbidden, permission, denied, unauthorized
  install      -> dependency, package, npm, pip
  failing      -> broken, error, crash
  audit        -> review, scan, inspect
  permissions  -> access, acl, authorization
  ftp          -> deploy, upload, publish
  ci           -> pipeline, workflow, automation
  ```

- スコア 0（クエリと共通トークンが一つもない）の skill は候補から除外す
  る。スコアが付いた skill を降順で並べ、同点は既存同様 name の昇順で安
  定させる。

#### 「ほぼ常に関連する」候補の選定

新しい公開関数を追加する。

```rust
pub fn near_universal(skills: &[Skill]) -> Vec<&Skill>
```

選定基準は次の 3 条件をすべて満たすことである。

1. description が trigger 形式で始まる。
   `^(use|apply)\s+(when|for|before)`（大小文字を区別しない）。
2. description が量化語を含む。`\b(any|every|all)\b`（大小文字を区別し
   ない）。
3. description の中に、固有の製品・技術名と見なせる語を含まない。文頭
   の `Use`/`Apply` を除く先頭が大文字の単語のうち、下記の一般的な略語
   一覧に含まれないものが一つでもあれば、固有名詞ありと判定する。

   ```
   PR, PRs, CI, CD, API, APIs, SDK, CLI, URL, URI, JSON, YAML,
   HTTP, HTTPS, SQL, UI, UX, ID, IDs, TDD, QA, CSS, HTML, JS, TS,
   OS, IO, DB
   ```

3 条件すべてを満たした skill の集合を、name の昇順に並べて返す。

安全弁として上限 `MAX_NEAR_UNIVERSAL = 20` を設ける。選定結果がこれを
超えた場合は name の昇順で先頭 20 件のみを返す。実装計画では、呼び出し
側が元の該当件数を知る手段（例えば `(Vec<&Skill>, usize)` のような戻り
値）までは持たせず、`Vec<&Skill>` を返す単純な形に narrow した。測定し
たコーパス（831 件）では 4 件しか該当せず実害はほぼ無いという判断によ
る受け入れ済みの縮小である。テストで上限そのものの動作（先頭 20 件へ切
り詰められ、name 昇順を保つこと）は確認する（受け入れ基準を参照）。

#### `lookup` への組み込み

`lookup` の検索経路（名前完全一致でも空クエリでもない場合）を次の順序
に変更する。

1. `near_universal(skills)` を求める。
2. BM25 で `q`（同義語展開後）をランキングし、上限 `MAX_RESULTS` 件を得
   る。
3. 2 の結果に含まれていない `near_universal` の要素を、2 の末尾へ追加す
   る（`near_universal` は元々 20 件以下なので、`MAX_RESULTS` を厳密な
   上限として守るわけではなく、2 の結果 + 追加分が実質的な出力件数にな
   る）。
4. 3 の結果を、既存の `list_candidates`（`MAX_LIST_BYTES` によるバイト
   上限、切り詰めた場合の明示）へそのまま渡す。

名前完全一致の経路、空クエリの経路には `near_universal` を混ぜない。ど
ちらも「クエリ自体が特定の対象を明示している」場面であり、無関係な常時
候補を割り込ませる理由がないためである。

ヒットが 0 件だった場合の「一致しなかった」メッセージについても、
`near_universal` が非空であれば検索結果と同じ扱いで含める。BM25 のスコ
アが全て 0 であっても、常時候補が一つも無いことはこの設計では起こらな
い限り、「一致なし、全件一覧」という現行の分岐に落ちる場面は減る。

## テスト

### `polaris-skills` または `polaris-tools`（BM25 本体）

- 同義語を介した一致: description に "secret" とだけ書かれた skill が、
  クエリ "credential" で見つかる。
- 語幹化を介した一致: description に "deploy" と書かれた skill が、クエ
  リ "deploying" で見つかる。
- name フィールドの重み: クエリの語が name にも description にも同程度
  現れる 2 skill のうち、name に現れる方が先に返る。
- 複数語クエリ: 現行の部分文字列一致では 0 件だった「クエリ全体が連続
  部分文字列として現れない」ケース（例: "how to add authentication" の
  ようなクエリで "authentication" を含む skill が見つかる）が見つかる。
- 上限: 20 件を超えてヒットする状況で、返るのがちょうど `MAX_RESULTS`
  件（+ `near_universal` の追加分）であること。

### `near_universal`

- 3 条件すべてを満たす skill が選ばれる。
- 量化語を欠く skill は選ばれない（trigger 形式ではあるが `any` 等を含
  まない description）。
- 固有名詞を含む skill は選ばれない（例: "Use when doing any task
  involving Supabase" は quantifier を満たすが選ばれない）。
- 一般的な略語一覧に含まれる語（例: "any API call"）は固有名詞と誤判定
  されず、他の 2 条件を満たせば選ばれる。
- 該当が 0 件のとき、空の Vec を返す（panic しない）。
- `MAX_NEAR_UNIVERSAL` を超える該当がある状況を人工的に作り、返るのが
  上限件数ちょうどで、name の昇順であることを確認する。

### `lookup` との統合

- `near_universal` に該当する skill が、それとは無関係なクエリの検索結
  果にも含まれる。
- 名前完全一致のときは `near_universal` の内容が混ざらない（body のみが
  返る）。
- 空クエリの一覧にも `near_universal` の内容が混ざらない（現行の一覧表
  示のみ）。
- `near_universal` の該当が 0 件のコーパスでは、現行の検索結果と挙動が
  変わらない（回帰確認）。

### `budget.rs`

このファイルの既存テストは変更しない。`assemble_always_on` の引数・戻
り値・不変条件は今回のスコープの外である。この設計が `budget.rs` に触
れないこと自体を確認する目的で、`AlwaysOn` のトークン数が
`near_universal` に該当する skill の有無・件数によって変化しないことを
確認する新しいテストを 1 本追加する（0 件・4 件相当・20 件相当の 3 パ
ターンを `assemble_always_on` へ渡し、いずれも同じトークン数になること
を確認する）。

### 評価コーパス（Rust 側）

Python での測定はオフラインの一回限りの検証であり、本番コードへは移植
しない。ただし「この設計が実装として意図通り動く」ことを確認する最小限
のケースとして、10〜20 件程度の実際の skill 例（trigger 形式・非
trigger 形式・同義語が要るクエリ・複数語クエリを含む）を Rust の統合テ
ストとして固定し、recall が退行しないことを回帰的に守る。831 件全体の
再現は求めない。

## 受け入れ基準

1. `lookup` の検索経路が BM25 ランキングで動く。複数語からなる自然文の
   クエリで、現行の部分文字列一致では見つからなかった skill が見つかる
   ケースが、統合テストとして少なくとも 3 件存在する。
2. 同義語展開と語幹化がそれぞれ独立したテストで確認できる。
3. `near_universal` が 3 条件（trigger 形式、量化語、固有名詞なし）で選
   定され、それぞれの条件を欠く反例つきでテストされている。
4. `near_universal` に上限があり、上限を超える人工的な入力でテストされ
   ている。
5. `lookup` の検索結果に `near_universal` の該当が常に加わり、名前完全
   一致・空クエリの経路には加わらないことがテストされている。
6. `budget.rs` の既存テストがすべて変更なしに緑のまま通る。加えて、
   `near_universal` の該当件数が `AlwaysOn` のトークン数に影響しないこ
   とを確認する新しいテストが 1 本追加されている。
7. `cargo test --workspace` が全件成功し、`cargo clippy --workspace
   -- -D warnings` と `cargo fmt --check` が clean である。
8. `docs/superpowers/CURRENT.md` の M3b 繰り越し 3 点（常時コンテキスト
   への静的カタログ混入の懸念、壊れた config.toml の巻き添え、YAML の
   端の挙動、byte 上限の再検討）のうち、少なくとも 1 点目（静的カタロ
   グ混入の懸念）は、この設計の「近傍候補は `lookup` の戻り値のみに載
   り `assemble_always_on` には触れない」という構成と、6 の新規テスト
   により応答済みとする。残り 3 点は本設計のスコープ外として
   `CURRENT.md` に残す。

## 保証しない範囲

- 831 件規模のコーパスでの recall 98% という数値そのもの。Rust 側の統
  合テストは個別ケースの回帰防止であり、母集団を再現した精度測定ではな
  い。
- 日本語を含む CJK クエリに対する検索精度の向上そのもの。部分文字列
  フォールバックにより既存の検索性は維持したが、BM25 のランキング能力
  （語幹化・同義語展開・name 重み付け）自体は CJK クエリには及ばない。
- `near_universal` の選定基準が将来のあらゆる description の書き方を捉
  えること。今回選ばれなかった `spec-first-development`（trigger 形式
  ではない書き方の実例）のように、同じ効能を持ちながら選定条件の外にあ
  る skill は残る。基準は経験的に有効だったものであり、完全性を主張し
  ない。
- `MAX_RESULTS` を超える候補があるときの全体最適な選び方。BM25 スコア
  順という単純な基準のみを用いる。
