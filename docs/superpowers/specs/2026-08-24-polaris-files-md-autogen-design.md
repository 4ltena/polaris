# polaris ディレクトリ別 `files.md` 自動生成 設計書

## 背景・目的

複数ファイル・複数ディレクトリにまたがるタスクでは、モデルが目的のファイルへたどり着くまでの探索コスト(`read`/`bash`での試行錯誤)が、常時コンテキストの外側で実質的なトークン消費として積み上がる。既存の `docs/filemap.md`(リポジトリ全体を1ファイルに集約、手動 `UPDATE_FILEMAP=1` 実行で更新)はこの探索コストを一定程度下げるが、単一ファイルであるため大規模リポジトリでは肥大化し、かつ更新はモデル自身の判断・手動コマンド実行に依存する。

本設計は、**ディレクトリごとに `files.md` を自動生成**し、モデルの判断・会話コンテキストのコストを一切かけずに(ハーネス側が決定的に、モデルに見えない形で)最新に保つ仕組みを追加する。

## スコープ

対象: このリポジトリ(`polaris` 本体)の `polaris-core`/`polaris-tools` クレートへの機能追加。M4(`spawn` サブエージェント基盤、実装済み)に依存する。

非対象(このスペックでは扱わない):
- ファイル削除・リネームへの追従(`files.md` の該当行が古いまま残る既知の制限として受け入れる)
- 「段階(ブレスト/設計/実装/レビュー等)」を明示信号として使う skill 選定の拡張(別途、次段階の作業として合意済み)
- `docs/filemap.md` 自体の変更・統合

## アーキテクチャ

```
[bash / write / edit ツール実行]
        │
        ├─ 実行前: 影響範囲のパス集合をスナップショット
        │
        ▼
   (ツール本体の実行)
        │
        ├─ 実行後: 同じ範囲を再スキャンし差分を取る
        │
        ▼
   新規ディレクトリ / 新規ファイルを検出
        │
        ▼
   検出された各ディレクトリについて
   spawn::run_one() を Rust コードから直接呼ぶ
   (SpawnTask { agent_type: "files-md-writer",
                task: "<dir path>",
                write_root: Some(<dir path>) })
        │
        ▼
   agents/files-md-writer/ subagent が
   ディレクトリ直下を read し、files.md を書く
        │
        ▼
   files.md のパスを .gitignore へ追記(未記載なら)
        │
        ▼
   元のツール呼び出しの結果をモデルへ返す
   (files.md 生成の過程・内容は会話コンテキストに一切現れない)
```

この経路は、モデルが `spawn` ツールを呼び出す既存の経路(Task 9)とは別物である。`dispatch` の外側、ツール実行のラッパー層でハーネスが直接 `spawn::run_one` を呼ぶ。モデルはこの subagent の存在自体を意識しない。

## コンポーネント

### 1. 差分検出(`crates/polaris-core/src/dir_watch.rs`、新設)

- `snapshot(root: &Path) -> DirSnapshot`: `root` 配下のパス集合(ファイル/ディレクトリの種別込み)を1回スキャンして返す。中身は読まない。
- `diff(before: &DirSnapshot, after: &DirSnapshot) -> DirChanges { new_dirs: Vec<PathBuf>, new_files_in_existing_dirs: Vec<PathBuf> }`
- スキャン範囲:
  - `bash`: サンドボックスの書込許可ルート配下(`SandboxPolicy` が `WorkspaceWrite` の場合のみ。`ReadOnly` なら差分検出自体をスキップ——書込が起きえないため)。
  - `write`/`edit`: 書き込み先パスの**親ディレクトリ1階層のみ**(1回の呼び出しで新規に作れるファイルは高々1つ)。

### 2. ハーネス側フック(`crates/polaris-core/src/agent.rs` の `dispatch` 呼び出し元、`run_loop`)

- 各ツール呼び出しの前後で `dir_watch::snapshot`/`diff` を呼ぶ(対象が `bash`/`write`/`edit` のときのみ)。
- 検出された `new_dirs` の各ディレクトリ、および「`new_files_in_existing_dirs` の親ディレクトリのうち既に `files.md` を持つもの」について、`spawn::run_one` を直接呼ぶ。
- 呼び出しは同期的(元のツール結果を返す前に完了を待つ)。
- `run_one` が `TaskOutcome::Failed` を返しても、元のツール呼び出し結果には一切影響しない(監査ログにのみ記録)。

### 3. `agents/files-md-writer/SKILL.md`(新設)

```yaml
---
name: files-md-writer
description: 単一ディレクトリ直下の各エントリ(ファイル・サブディレクトリ)を1文で要約した files.md を書く。
allowed-tools: read write
metadata:
  polaris-access: read-write
  polaris-tier: low
  polaris-wall-seconds: "60"
  polaris-max-turns: "4"
  polaris-continuation: "denied"
  polaris-output: references/result.schema.json
---
```

本文: 与えられたディレクトリを `read`(ディレクトリ一覧)し、直下の各ファイル・サブディレクトリについて1文の概要を作り、`<dir>/files.md` として `write` する。サブディレクトリの概要は、そのサブディレクトリ自身の `files.md` があればその冒頭の説明を要約し、無ければディレクトリ名から推測する短い説明にとどめる。

出力スキーマ(`references/result.schema.json`): `{"path": string, "status": "ok"}` 程度の最小構成。この戻り値はモデルの会話には表示されず、監査ログにのみ残る。

### 4. `.gitignore` 追記

- 生成した `files.md` の相対パスが、リポジトリルートの `.gitignore` に(あるいはより近い階層の `.gitignore` があればそちらに)既に含まれていなければ1行追記する。
- 追記は冪等(既存の場合は何もしない)。
- 具体的なパターンとして `**/files.md` のような包括パターン1行を、初回生成時にリポジトリルートの `.gitignore` へ追記する方式を採る(ディレクトリごとに個別パスを追記すると `.gitignore` 自体が肥大化するため)。既にそのパターンが存在すればスキップ。

## データフロー・更新ポリシー

- **新規ディレクトリ検出時**: そのディレクトリ自身の `files.md` を新規生成する。既存の親ディレクトリに `files.md` があれば、その親の一覧にも新しいサブディレクトリの行を反映するため親の `files.md` も再生成する。親に `files.md` がまだ無ければ何もしない(親自身がまだ観測対象になっていない)。
- **既存ディレクトリへの新規ファイル検出時**: そのディレクトリに既存の `files.md` があれば全体を再生成する(部分パッチではなく、対象ディレクトリを `read` し直して丸ごと書き直す——整合性バグを避けるため)。`files.md` が無ければ何もしない。
- **削除・リネームへの追従なし**(既知の制限、スコープ外として明記済み)。

## エラー処理

- `files-md-writer` の実行失敗(プロバイダエラー・スキーマ不一致2回失敗等)は、元のツール呼び出し結果に一切影響しない。ベストエフォートの副作用として扱う。
- 失敗時の実害は「次にそのディレクトリを見る際の探索コスト削減が効かない」だけであり、機能上の破綻はない。

## テスト方針

1. 差分検出ロジック(`dir_watch::snapshot`/`diff`)を、実際の subagent 呼び出しなしにフィクスチャディレクトリで単体テストする。
2. 検出された新規ディレクトリに対し、正しい `SpawnTask { agent_type: "files-md-writer", write_root: <dir> }` が組み立てられ `run_one` が呼ばれることを、モックプロバイダで確認する統合テスト。
3. subagent 実行が失敗しても元のツール呼び出し自体は失敗しないことを確認するテスト(受け入れ基準の柱)。
4. `.gitignore` への追記が冪等であることのテスト。
5. 実サンドボックスを使い、小さな実ディレクトリに対して `files.md` が実際に書き出され、期待する形式になることを確認するテスト(Task 12 の実サンドボックステストと同じ形)。

## 受け入れ基準

1. `mkdir`(文字列解析ではなく、bash 実行前後のファイルシステム差分で検知)で新規に現れたディレクトリに、次のツール呼び出しが返るまでに `files.md` が存在する。
2. `write`/`edit` で既存ディレクトリに新規ファイルが作られた場合、そのディレクトリに既存の `files.md` があれば同様に更新される。
3. `files-md-writer` の生成失敗は、元のツール呼び出しの成否に一切影響しない。
4. 生成された `files.md` は `.gitignore` に自動的に含まれ、`git status` に新規未追跡ファイルとして現れない。
5. この機能追加によって、既存の常時コンテキスト予算(990トークン、`budget.rs` の不変条件テスト)には一切影響がない(この機構はツール呼び出しの前後で動くハーネス内部処理であり、モデルへの常時コンテキストには何も追加しない)。

## 既知のリスク

- **bash 呼び出しごとの再帰スキャンコスト**: `bash` はサンドボックスの書込許可ルート配下を毎回前後スキャンする。ルートが大きなディレクトリツリー(例: 依存パッケージを含むプロジェクト)の場合、1回の `bash` 呼び出しごとに壁時計コストが積み上がる可能性がある。実装計画側で、`.git`・既知の依存ディレクトリ(`node_modules`・`target` 等)を除外する、またはスキャンに実測の時間上限を設けるといった軽減策を検討すること。これは受け入れ基準に含めていないが、実装時に実測し、許容できない場合はこの設計へ差し戻す。
- 書込許可ルートが複数(`SandboxPolicy` が複数の write root を持つ場合)は、それぞれを独立にスキャンする。

## 見送った代替案

- **`mkdir` コマンド文字列の構文解析による検知**: `mkdir -p a/b/c` や複合コマンドでの検知漏れ、`write` 経由の新規ディレクトリを拾えない制約があるため、ファイルシステム差分方式を採用した。
- **非同期(バックグラウンド)生成**: モデルのターン遷移は速くなるが、「`files.md` がまだない間に次のターンが進む」レースや完了検知の仕組みが別途必要になる複雑さに見合わないと判断し、同期方式を採用した。
- **`spawn` ツール経由(モデル自身が `spawn` を呼ぶ)**: 会話コンテキストへの追加コスト(`spawn` の呼び出し・結果表示)が発生し、「探索コストを下げる」という目的に反するため、ハーネスがモデルを介さず直接 `spawn::run_one` を呼ぶ方式を採用した。
