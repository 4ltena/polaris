# 変異で確かめる

テストが通ることは、テストが効いていることを意味しない。否定だけを
主張するテストは、対象が何もしなくても通る。拒否を確かめるテストは、
すべてを拒否する実装でも通る。

## 手順

1. 直したコードを意図的に壊す
2. **壊れた内容がディスクに乗ったことを確かめる**（`grep` か `md5`）
3. ビルドが実際に走り直したことを確かめる。古い成果物が使い回されると、
   変異が効いていないのに効いたように見える
4. 意図したテストが、意図した理由で落ちることを確かめる
5. 戻し、ツリーが元どおりであることを確かめる

適用に失敗した変異は、捕まらなかった変異と外から見て区別がつかない。
2 を飛ばすと、この2つを取り違える。

## 両方向を試す

片側だけでは足りない。「拒否されるはずのものが拒否される」ことと
「許可されるはずのものが許可される」ことを対で見る。実際に、
サンドボックスの拒否テストは通るのに、ヘルパが起動すらできていない
という欠陥が 254 件緑のまま出荷された例がある。

特に試す価値があるのは「正常終了して何もしない」変異である。終了
コード 0、標準エラー空。内容を確かめる表明が無ければ、これは捕まらない。

## 代役に気をつける

テスト用の代役は本物より制約に強い。`/bin/sh` の代役はどんなサンドボックス
プロファイルでも起動するが、本物の Rust バイナリは起動できないことがある。
本物を本物の制約の下で走らせる経路を最低1本持つ。
